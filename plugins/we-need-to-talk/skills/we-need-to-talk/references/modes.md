# Tri-Grill modes

모드는 질문의 관점이며 별도 에이전트나 실행 프로세스가 아니다. 같은 에이전트가 관점을 바꾸고 같은 기록을 이어 쓴다.
현재 관문의 목적을 한 문장으로 소개하고 해당하는 질문만 선택한다.

## VC — Scope Guillotine

핵심 질문: **“그거 꼭 지금 다 만들어야 해요?”**

- 실제 사용자·문제·이번 결과와 성공 기준을 확인한다.
- 추가 기능이 핵심 결과에 필요한지 묻고, 최소 범위와 제외 범위를 사용자와 정한다.
- 검증되지 않은 수요·성능·기한은 가정으로 남긴다. 필요하면 작게 검증할 방법을 묻는다.
- 상업 제품이 아닌 취미·내부 도구·연구에도 그 목적에 맞는 가치를 인정한다.
  수익화를 강요하거나 최소한의 보안·복구 요구를 무조건 잘라내지 않는다.

완료 근거: 누구에게 어떤 결과를 줄지, 이번 범위와 제외 범위, 성공을 관찰할 방법이 있다.
예시 질문: “협업과 자동 동기화를 둘 다 빼도 첫 사용자가 얻어야 할 한 가지 결과는 뭔가요?”

## Partner — Consistency Grill

핵심 질문: **“기존 코드랑 말이 다르잖아요.”**

- 좁혀진 범위를 기존 계약, 상태 소유권, 데이터 흐름, 인터페이스와 대조한다.
- 변경이 필요한 부분과 유지할 제약을 구별하고 실제로 충돌하는 근거의 ID를 보여준다.
- 문서와 코드가 다른 경우 현재 동작과 의도한 동작을 별도로 기록한다.
- 기존 구현이 없으면 설계할 계약을 묻는다. 비교할 파일이 있는 것처럼 말하지 않는다.

완료 근거: 핵심 흐름과 책임·입출력·상태가 구체적이며 영향 범위의 차단 모순이 해결돼 있다.
예시 질문: “상태는 런타임 소유라던 D-003과 화면에서 직접 저장한다는 답이 충돌해요. 쓰기 책임은 어디에 둘까요?”

## Security — Catastrophe Drill

핵심 질문: **“이러다 프로세스 죽으면 어쩔 건데요?”**

- 선택한 범위에서 실제로 가능한 프로세스 종료, 타임아웃, 응답 유실, 중복 실행, 권한 거부를 고른다.
- 필요한 경우 신뢰 경계, 비밀정보, 권한 최소화, 외부 입력과 데이터 보존을 확인한다.
- 실패를 누가 감지하고 무엇을 재시도·취소·복구하는지, 사용자는 무엇을 보게 되는지 묻는다.
- 절대 허용하지 않을 결과와 감수할 손실 범위를 구별한다. 장애 시나리오를 끝없이 늘리지 않는다.

완료 근거: 관련 실패 조건, 허용 결과, 복구 책임과 확인 가능한 수용 기준이 정해져 있다.
예시 질문: “서버는 저장했는데 응답만 사라졌어요. 재시도할 때 같은 요청이라는 걸 어떻게 알아보죠?”

이 관문은 설계 면담이다. 코드 취약점 스캔, 침투 테스트, 운영 장애 재현이나 보안 인증의 완료 증거가 아니다.

## Gauntlet — 세 관문을 이어가기

새 세션에서는 사전 조사 후 `vc → partner → security` 순서로 진행한다. 각 관문 안에서 공통 루프를 돈다.
관문 하나를 질문 한 개 또는 문답 한 회차로 제한하지 않는다. 강도별 예산은 세 관문의 합계다.

인덱스에 각 관문의 상태와 근거를 남긴다:

| 상태 | 뜻 |
| --- | --- |
| `pending` | 선택된 흐름에 포함됐지만 아직 검토하지 않음 |
| `active` | 현재 검토 중 |
| `complete` | 해당 관점의 완료 근거가 충족됨 |
| `deferred` | 사용자 요청으로 검토를 보류함 |
| `needs-review` | 앞선 근거가 변경돼 재검토가 필요함 |
| `not-reviewed` | 현재 단일 모드의 검토 범위에 포함되지 않음 |

1. 관문을 마칠 때 핵심 결정과 남은 쟁점을 먼저 저장한다. 다음 관점으로 이동한다고 짧게 안내한다.
2. 이미 충분한 근거가 있으면 질문 없이 `complete`로 표시할 수 있지만 근거 ID와 이유는 남긴다.
3. 차단 결정이 보류되면 해당 관문은 `deferred`로 남긴다. 독립적인 다음 검토는 진행할 수 있다.
   빠진 결정을 임의로 채워 의존하는 검토까지 완료하지 않는다.
4. 뒤 관문에서 앞선 결정이 바뀌면 그 결정에 의존한 완료 관문을 `needs-review`로 바꾸고 영향받은 부분만 다시 검토한다.
   예: 복구를 위해 서버 저장을 추가하면 VC의 범위와 Partner의 데이터 계약을 다시 확인할 수 있다.
5. 사용자에게 필요 없는 검토를 반복하지 않는다. 변경이 한 관문에만 국한되면 다른 관문은 그대로 유지한다.

## 전환과 재개

- `--mode security` 또는 “이제 장애 처리만 보자”는 검토 범위를 바꾸라는 요청이다. 이전 결정은 유지한다.
- 단일 모드에서 gauntlet로 바꾸면 유효한 관문 기록을 재사용하고 남은 관문부터 진행한다.
- gauntlet에서 단일 모드로 바꾸면 미검토 범위를 남긴다. 실제로 끝낸 관문의 이력은 지우지 않는다.
- `--resume`은 저장된 모드와 관문에서 이어간다. 모드 필드가 없는 이전 버전의 세션은 `partner`로 이어가고
  나머지 관문은 `not-reviewed`로 표시한다. 사용자가 gauntlet 전환을 요청하면 적용한다.
- 최종 명세에 검토 범위와 관문 상태를 요약한다. `complete`와 전체 구현 준비 상태를 구별한다.
