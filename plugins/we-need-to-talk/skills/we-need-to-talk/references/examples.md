# 면담 예시

아래 대화와 기록은 모두 가상 예시다. 현재 프로젝트의 증거로 인용하지 않는다.

## 근거가 없는 새 프로젝트

사용자: “재시작해도 기록이 남는 메모 앱, 스펙 털어줘.”

사전 기록: “기존 구현·문서 없음. 재시작 후 보존은 사용자 요구이며 저장 방식은 미정.”

질문: “재시작 뒤에도 남길 기록의 범위부터 정할게요. 저장 버튼을 누른 메모만인가요,
아직 입력 중이던 초안도 포함인가요?”

없는 데이터베이스나 충돌을 만들어 압박하지 않는다.

## 결정 변경을 추궁과 구별

R-001 사용자: “초안은 디스크에 저장하지 마.” → D-001, active.

R-002 사용자: “생각 바꿨어. 초안도 로컬에 저장하고 재시작하면 복원해.”

먼저 저장할 내용:

- D-001: superseded, D-002로 대체.
- D-002: 초안을 로컬에 저장하고 재시작 시 복원. R-002의 사용자 직접 지시.
- Q-001: 저장 시점과 손실 허용 범위 미정.
- 기존 최종 명세가 있다면 stale 표시.

다음 질문: “변경은 반영했어요. 입력 중 강제 종료되면 직전 몇 초까지의 손실을 허용할까요?”

변경 자체를 사용자의 실수로 몰거나 다시 허락받지 않는다.

## 실제 모순

R-001: “어떤 저장소에도 초안을 남기지 않는다.”
R-002: “프로세스가 죽어도 모든 초안을 반드시 복원한다.”

질문: “D-001의 저장 금지와 이번 복원 요구가 충돌해요. 저장 금지 범위를 바꾸려는 건가요,
아니면 복원 가능한 범위를 줄이려는 건가요? 다른 복원 경로가 있다면 설명해주세요.”

동시에 충족할 근거가 없다는 쟁점으로 기록한다. 사용자의 의도를 먼저 단정하지 않는다.

## 비용을 드러내는 선택지

“다른 기기에서도 초안을 이어 쓰려면 저장 범위를 정해야 해요.”

- 로컬만 보존: 서버 운영은 필요 없지만 다른 기기에서 이어 쓸 수 없음.
- 서버 동기화: 기기 간 복원 가능, 계정·동기화 충돌·삭제 정책을 추가로 결정해야 함.
- 파일 내보내기: 사용자가 직접 옮길 수 있음, 자동 동기화는 제공하지 않음.

실제 요구에 맞는 선택지만 제시한다. ‘구현 비용 두 배’처럼 검증하지 않은 수치를 붙이지 않는다.

## “알아서 해”, “나중에”, “그만”

- “자동 저장 주기는 네가 정해”: 위임을 기록하고 선택한 주기와 이유를 명시한다.
  사용자 발언을 “주기 3초를 승인했다”로 바꾸지 않는다.
- “계정 정책은 나중에”: 계정 구현에 차단되는 Q를 남기고 독립적인 편집 동작은 계속 정리한다.
- “오늘은 여기까지”: 현재 답변을 저장하고 paused, 재개 경로를 전달한다. 추가 압박 질문을 하지 않는다.
- “미정이어도 최종 문서 줘”: incomplete 문서를 작성하고 남은 차단 쟁점을 본문에 명시한다.

## 저장 실패와 재개

테마 파일은 저장됐지만 인덱스 쓰기가 실패한 경우:

“R-003 답변은 `draft-storage.md`에 저장됐고 인덱스 갱신은 실패했어요.”라고 정확히 알린다.
다음 질문을 보내지 않는다. 재개 시 테마 파일의 R-003과 인덱스를 맞추고 그 답변을 다시 묻지 않는다.

## 매운맛의 차이

같은 쟁점: 타임아웃 후 사용자가 다시 누르면 중복 요청이 생길 수 있음.

- mild: “타임아웃 뒤 재시도에서 중복 실행은 어떻게 막을까요?”
- spicy: “화면만 재시도 가능하게 하면 같은 요청이 두 번 실행될 수 있어요. 중복을 판정할 기준은 뭔가요?”
- hell: “중복은 없다고 했는데, 응답만 유실되면 서버는 이미 실행했을 수 있어요.
  재시도와 새 요청을 가르는 기준, 그리고 그 기준을 보존할 책임은 어디에 둘 건가요?”

hell에서도 사용자를 모욕하지 않고 실제 반례를 구체화한다.
