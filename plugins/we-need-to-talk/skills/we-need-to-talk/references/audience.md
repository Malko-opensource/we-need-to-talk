# Feynman Probe와 청중 맞춤 설명

같은 사실을 이해하기 쉬운 관점으로 설명한다. 청중에 맞춘다는 이유로 조건이나 불확실성을 삭제하지 않는다.

## 청중 선택

사용자가 지정한 청중을 우선하고, 없으면 대화에서 드러난 배경에 맞춘다.
직함은 관심사에 대한 단서일 뿐 지식 수준의 증거가 아니다. 필요할 때만 원하는 설명 깊이를 묻는다.

| 청중 예시 | 어휘와 관심사 | 적합한 확인 |
| --- | --- | --- |
| 개발자·코딩 에이전트 | 주체, 상태, 소유권, 경계, 관찰 가능한 조건 | 누가 완료를 확정하며 재시도는 누가 소유하는가 |
| 매니저·경영진 | 고객 영향, 범위, 비용의 원인, 일정 의존성 | 무엇을 포기하며 어떤 위험을 수용하는가 |
| 디자이너·PM | 화면 상태, 사용자 행동, 실패 안내, 복구 경로 | 실패했을 때 무엇을 보고 다음에 무엇을 하는가 |
| 비전문가·초심자 | 일상 어휘와 작은 예시, 필요한 용어의 정의 | 시작부터 결과까지 구체적인 한 번의 흐름 |
| 사용자가 지정한 다른 청중 | 해당 청중의 목표와 익숙한 맥락 | 결정에 필요한 이해만 확인 |

## Feynman Probe

트리거는 전문용어 자체가 아니라 **그 말로 중요한 동작이 정해지지 않은 경우**다.

1. 빠진 동작을 특정한다. 예: “자동 복구”만 있고 재시도 주체가 없다.
2. 한 가지를 묻는다. “주문서를 전달하는 과정처럼, 누가 받고 누가 다시 보내는지 말해볼까요?”
3. 답변을 실제 구성요소와 순서로 옮기고 빈칸만 다음 질문으로 남긴다.
4. 답변을 먼저 기록한다. 새로 발견한 빈칸은 Q-ID, 추천은 제안으로 구분한다.

“몰라, 설명해 줘”라면 에이전트가 작은 예를 먼저 제공한다.
“내가 비유를 못하겠어”는 기술을 모른다는 증거가 아니다. 직접적인 용어로 정확히 설명했으면 충분하다.
설명을 원치 않거나 이미 결과를 이해하고 위임했으면 추가 시험 없이 진행한다.
보안·복구 주제라고 항상 파국 비유를 강요하지 않는다.

## 비유의 네 단계

1. **직관**: “아직 저장하지 않은 문서를 화면에만 띄워둔 것과 비슷해요.”
2. **대응**: “여기서 화면의 내용은 RAM의 초안이고, 저장은 디스크나 서버에 기록하는 단계예요.”
3. **한계**: “이 비유는 초안의 다른 사본이 없고 자동 저장도 없다는 조건에서만 맞아요.
   이미 서버에 저장한 원본이나 다시 계산할 수 있는 캐시 전체가 사라진다는 뜻은 아니에요.”
4. **결과**: “프로세스가 종료되면 미저장 초안은 잃을 수 있어요. 이 손실을 허용할지, 저장을 넣을지 정해야 해요.”

비유는 근거를 대신하지 않는다. 실제 보장과 가정을 이어 적는다.
정전과 프로세스 크래시, 캐시와 원본, 유실과 지연을 같은 실패로 섞지 않는다.
측정하지 않은 “2배 빨라진다”나 “40% 개선”은 쓰지 않는다.

## Readback Check와 함께 사용

Feynman Probe는 흐름의 빈칸을 찾는다. Readback Check는 선택의 결과가 기대와 맞는지 확인한다.
한 상황에서 둘 다 필요하면 하나의 구체적인 질문으로 합친다. 회차당 총 1~2개 질문 제한은 그대로다.
예: “초안이 메모리에만 있는 상태에서 앱이 종료되면, 다시 켰을 때 사용자에게 무엇이 남아 있나요?”
